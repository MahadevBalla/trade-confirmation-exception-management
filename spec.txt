1. Quick answers on open-source technology choices
Recommended stack
Use Apache Kafka for event streaming and Apache CouchDB for the NoSQL document database. Kafka is an Apache Software Foundation project under Apache License 2.0, and CouchDB is an Apache project with native JSON/HTTP APIs and Apache License 2.0. MongoDB Community Server is usable for many internal learning projects, but its current SSPL license is not OSI-approved according to MongoDB’s own FAQ, so it is not the cleanest choice for a “fully open-source” university brief.

2. Business problem
Financial institutions process large volumes of post-trade confirmations. A confirmation must reflect the agreed economic and non-economic terms of a trade. When trade data is incomplete, inconsistent, delayed, or cannot be matched to a valid confirmation template, the trade becomes an exception and requires investigation.
This capstone asks students to design a generic educational platform that does not submit trades from a UI. Instead, trade messages arrive through an event broker, are processed by backend services, and are surfaced in dashboards after automated enrichment, validation, confirmation generation, and exception classification have been attempted.
3. Learning objectives
Practice event-driven system design with producers, consumers, topics, replay, dead-letter queues, idempotency, and audit trails.
Model realistic-but-synthetic post-trade messages using FpML-inspired JSON rather than full FpML XML.
Build a Java backend with clean service boundaries and a React frontend focused on operational workflows and dashboards.
Design exception taxonomies, recommendation rules, and work-item linkage while leaving room for student innovation.
Demonstrate non-functional thinking: scalability, observability, resilience, security, auditability, and performance.

8. MVP scope
MVP philosophy
Keep the MVP small but end-to-end. It should prove the event-driven pattern, canonical message model, STP/exception branch, dashboard, audit, replay, and deployment story without asking students to solve every product, workflow, or AI problem.
One product family, for example FX Option or Equity Swap-like synthetic messages.
Three Kafka topics minimum: raw trades, processed outcomes, and dead-letter events. More topics are encouraged if useful.
CouchDB databases/documents for trades, confirmations, exceptions, work items, reference data, and audit events.
Rule-based enrichment and validation using mock CSV/JSON reference data.
At least six exception categories and ten sample exception scenarios.
Basic classification using deterministic rules; optional scoring is stretch.
Mock work-item linking with locally generated work item IDs.
React dashboard with summary cards, trade detail, exception list, and manual review screen.
Audit trail and replay button for selected safe scenarios.
Representative load test with a subset volume, plus written explanation of how the architecture scales toward the target NFRs.

Multiple product families and configurable product-specific mandatory fields.

10. FpML-inspired JSON canonical message model
Students should not implement full FpML XML. Instead, they should borrow FpML’s ideas: reusable building blocks, common naming conventions, product-specific sections, party/trade identifiers, economics, lifecycle events, and confirmation status. The goal is a teachable JSON model that remains close enough to post-trade concepts to be realistic.
{   "messageHeader": {     "messageId": "MSG-000001",     "correlationId": "CORR-10001",     "eventType": "NEW_TRADE",     "schemaVersion": "capstone-fpml-json-1.0",     "createdTimestamp": "2026-01-15T10:30:00Z"   },   "trade": {     "tradeId": "TRD-10001",     "sourceSystemTradeId": "SRC-77881",     "productType": "FX_OPTION",     "tradeDate": "2026-01-15",     "effectiveDate": "2026-01-17",     "maturityDate": "2026-04-17",     "parties": [       { "partyRole": "BANK", "partyId": "PTY-BANK-001" },       { "partyRole": "COUNTERPARTY", "partyId": "PTY-CP-101" }     ],     "economics": {       "notionalAmount": 1000000,       "notionalCurrency": "USD",       "buySell": "BUY",       "optionType": "CALL",       "strike": 1.085,       "underlier": "EUR/USD",       "premiumAmount": 12000,       "premiumCurrency": "USD"     },     "nonEconomicTerms": {       "jurisdiction": "GENERIC",       "confirmationMethod": "ELECTRONIC",       "templateHint": "FX_OPTION_STANDARD"     }   } }
Tip: students may add fields, but every new field should have a reason: validation, enrichment, confirmation generation, exception classification, audit, or reporting.
11. Tips for identifying and modelling fields
Start from the confirmation question: What would both parties need to agree on for this trade? Those fields belong in economics or non-economic terms.
Separate identifiers from economics. Trade ID, correlation ID, message ID, party ID, and account ID are not product economics, but they are essential for traceability.
Distinguish mandatory from optional by product type. A strike is mandatory for an option but not for every trade type.
Record provenance. For enriched fields, store source, timestamp, and whether the value was supplied, derived, or defaulted.
Design for exceptions. If a missing value should create a work item, it deserves a clear field name and reason code.
Avoid overfitting to one sample. Model common fields globally, product-specific fields in a product section, and derived/temporary values separately.
Prefer explicit units and currencies. Use amount + currency, date + convention, rate + rate type, and quantity + unit where appropriate.
Keep schema evolution in mind. Include schemaVersion and avoid breaking existing sample messages when adding new optional fields.
Use FpML as inspiration, not a copy. Borrow concepts such as trade header, party trade identifiers, product views, and confirmation status, but keep JSON small and student-friendly.

16. Sample datasets
Synthetic trades: at least 500 records for MVP; include valid, missing-field, invalid-reference, missing-template, duplicate, malformed, and delayed examples.
Mock reference data: counterparties, instruments, product eligibility, template catalogue, and basic SLA/priority configuration.
Expected outcomes: a small labelled dataset that states whether each sample should STP, generate an exception, or enter dead-letter handling.
Dashboard seed data: aged exceptions, root-cause categories, work-item statuses, and replay history.
17. Implementation guardrails
Do not hard-code all answers; make validation and classification rules inspectable and extendable.
Do not build a UI trade-entry screen; trade intake is event/message-driven only.
Do not include real client, bank, trade, or proprietary system data.
Do not overbuild workflow orchestration in MVP; keep work-item handling generic and mockable.
Do not treat AI as a substitute for data modelling; classification must be explainable.
